## Lighthouse — the four required numbers

| profile | accessibility | performance |
|---|---|---|
| desktop | **96** | **100** |
| mobile | **96** | **94** (four runs: 94 · 94 · 97 · 94) |

Three of the four clear the ≥ 95 floor. **Mobile performance does not: it sits at 94, median of four runs.**

- Desktop detail: FCP 0.7 s (0.98) · LCP 0.7 s (0.99) · TBT 0 ms (1) · CLS 0 (1) · Speed Index 0.7 s (1).
- Mobile detail: FCP 2.5 s (0.69) · LCP 2.5 s (0.90) · TBT 0 ms (1) · CLS 0 (1) · Speed Index 2.5 s (0.98).
- The whole mobile deficit is First Contentful Paint, and the whole of FCP is one render-blocking third-party
  request: `fonts.googleapis.com/css2?family=Bodoni+Moda…&family=JetBrains+Mono…`, 2 134 B, **792 ms** of blocking
  under Lighthouse's mobile throttle (4× CPU, slow 4G), against 152 ms for the site's own 6 767 B stylesheet. The
  run that scored 97 is the run where that request came back fast (FCP 1.4 s). The site's own JS contributes
  nothing measurable: TBT is 0 ms on every run.
- **The obvious mitigation is already in place.** `index.html` lines 11–12 carry
  `<link rel="preconnect" href="https://fonts.googleapis.com">` and
  `<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>`, and the stylesheet uses `display=swap`.
  Getting past 95 reliably would mean self-hosting the two families, which changes the build's asset policy
  (§13's stack sources them from Google) and is an owner decision, not an orchestrator one. Carried as R-P6-8.
- Not counted against the floors, recorded for completeness: SEO 91 and Agentic Browsing 67 on both profiles, both
  from the same cause — `vite preview` serves `index.html` for `/robots.txt` and `/llms.txt`, so Lighthouse parses
  markup as those files and fails them. §12 already records the robots.txt miss as an artefact of the preview
  server. Best Practices is 100 on both profiles.

### Why accessibility is 96 and not 100

One audit fails, on both profiles, and it is a recorded decision, not an oversight:

```
target-size  score 0  "Touch targets do not have sufficient size or spacing."
  section#top > ol.steps > li > a   46 x 24
  section#top > ol.steps > li > a   62 x 24
```

These are the hero's step anchors. **D-21** gives them a 24 px hit box — `padding-block: calc((24px - 1lh) / 2)`
with the matching negative margin — because 44 px would move every row of a list whose 18 px pitch is §4 geometry
protected by ruling 2. 24 px is the WCAG 2.5.8 (AA) minimum and the anchors meet it; Lighthouse's `target-size`
additionally wants clearance between adjacent targets, which a list on an 18 px pitch cannot give. The trade-off
was ruled, is recorded in `DESIGN.md` §3, and costs four points. No other accessibility audit fails.

## CDP accessibility tree

**Headings.** Four in the tree, one h1 and three h2, in document order:

```
  level 1  "Two models are good. A system is better."
  level 2  "BEFORE ANY CODE"
  level 2  "AFTER EVERY TASK"
  level 2  "FOR THE WHOLE RUN"
```

Three level-2 headings exist, one per section, each named from its own title and nothing else — the eyebrow spans
(`02` / `03` / `04`) do not enter the name. **One deviation from T-603's wording:** the check asks for the names
`Before any code` / `After every task` / `For the whole run`, and the tree carries them uppercase. The names come
from the DOM text, and §16.10 specifies that copy verbatim in capitals, which REQ-013 requires; §16.9's mixed-case
form and §16.10's capitals are inconsistent inside the sheet. The build followed the copy. Not changed here —
reconciling them means either breaking REQ-013 or adding an `aria-label`, and both need the owner. Carried as
R-P6-9.

**Decoration is out of the tree.** Exact-name search over the 959 non-ignored AX nodes:

```
  "// contracts over context"                0 nodes
  "// not its own judge"                     0 nodes
  "// your tools, your models, your rules"   0 nodes
  "§02"                                      0 nodes
  "auth-guard"                               0 nodes
```

All six `.marg` whispers, all three `.stop` coordinates, the three `.aura` layers and the rail sit under
`aria-hidden="true"` and reach the tree not at all. `canvas.dots` contributes **no** node: six canvases, zero
`canvas` roles in the tree (the three `image` roles are the hero's ghost stages). "T002" does appear twice as an
exact node name — from the panel's own content, `id: T002` and `task: T002`, which is real copy, not the stop.

**One finding that is by design, checked rather than assumed.** The three `p.marg-list` rail lists —
`SPEC / PLAN / BRIEFS / EXECUTE / REVIEW`, `VALIDATE / RETRY / ESCALATE / EVIDENCE / IMPROVE`,
`LIMITS / BUDGET / RETRIES / REVIEW / EVIDENCE` — are NOT aria-hidden and do reach the tree, one static text per
line. That is correct: §16.9 item 1 puts the `aria-hidden` requirement on `.marg`, and T-603's list names `.marg`,
`.stop`, the `.aura` content and the rail. A marg-list is page vocabulary a screen-reader user should get, not a
whisper. Verified, not fixed.
