# Changelog

> Entries below `[Unreleased]` describe earlier versions. They name commands, config keys
> and documents that have since been removed; the current surface is what the user guides
> under `docs/` describe.

## [Unreleased]

### Added

- **npm package.** SPLITBRIEF ships as the `splitbrief` npm package with provenance, and the package includes the user guides.
- **One planning session with a typed plan.** Every run plans in one session. Before the plan, the planner may ask as many questions as it needs, in at most two rounds, each with a default; an empty `⏎` takes the defaults. The planner then answers with one typed plan. SPLITBRIEF checks it and writes it as `plan.json`, rendered as `plan.md` and `tasks.md`. A plan that fails its checks goes back to the planner once, and a second failure halts the run. `splitbrief spec` runs the same session without a build. See [The planning session](./docs/WORKFLOW.md#3-the-planning-session).
- **The plan card.** One approval before the build: **Approve plan**, **Request changes**, **Edit plan.json** (checked before it saves) or **End run**. Approving the plan also confirms the protected writes that it lists, and the card names them. A headless run approves the card unattended.
- **One workspace per run, applied once.** Every brief, retry, check and review of a run uses one worktree or staged copy. A passing review makes the result ready to apply, and the result menu offers **Apply**, **Show diff** and **Discard**. Apply merges your own checkout edits first, checks and reviews a changed result again, then writes with a hash guard and a backup. A conflict halts for per-file resolution, and a partial write offers restore or retry. Discard and End run keep `run.patch`. See [Apply](./docs/WORKFLOW.md#apply).
- **Checkout mode.** `workflow.isolation: none` ("your checkout") lets the implementer edit your checkout directly. Checks and review run there, and a passing review closes the run with no Apply. An edit between calls is a warning, a git write during a call halts the run, and every revert first saves the bytes it replaces. Settings cycles *Isolation* through worktree, staged copy and your checkout. For a stack that the worktree cannot serve, readiness recommends `none`.
- **Consults instead of fixed escalation tiers.** A brief that fails or reports `blocked` gets one read-only consult: guidance and a retry, a rewrite, a split into 2 or more subtasks, a check-only verification, one question to you, or an answer that the brief cannot be done. The planner answers every consult, the consult of a fix task included. It answers again after every failed attempt, with no limit on answers, and it sees its earlier answers and the attempts that followed them. You are asked only when the planner needs your answer, when it answers that a brief cannot be done, or when a seat is down with no fallback. A brief that cannot be done stops with `Needs you · <task>: the planner says it cannot be done` and the planner's reason. A question that nobody answers stops the brief with `Needs you · <task> needs your answer` and shows the question; **Try again** runs the brief again with your typed answer, and the planner sees that answer if the attempt fails. When a consult call fails, the run halts on PLAN, and a seat switch moves PLAN.
- **Decide for me.** The planner question card and the `Needs you` panel offer **Decide for me**. After you choose it, the run asks you nothing until it ends, also after a stop and a continue, in the terminal and with `--plain` or `--json`. Planning questions take their defaults. A brief's question with no default goes back to the brief, and its implementer decides on the next attempt. A review's question with no default goes back to the next review, and the reviewer decides. When the planner says a brief cannot be done, it names the next step: skip the brief, which the transcript and the review show with its reason, or end the run. A seat with no fallback that the run can take, which hits its usage limit again after it waited for the reset, waits for the next reset, unless you continue with `--on-seat-down halt`. A reply you type still goes to the planner as your answer, and words you type to continue a stopped run answer its halt. See [Decide for me](./docs/APPROVAL-AND-RECOVERY.md#decide-for-me).
- **The decisions ledger.** An implementer reports where it departed from its brief and why. The decision joins the ledger with the brief's id, with no extra planner call, and reaches every later brief, consult and review. The reviewer judges each one against the code.
- **The plan names the project gate.** The planner names the commands that the project's own scripts or CI run to verify a change (`V1`, `V2`, …), as many as the project needs. The plan card and `plan.md` show them. Before the final review, SPLITBRIEF runs them in the run workspace, in any language: for example `mvn test`, `gradle test`, `composer test`, `bundle exec rspec`, `make check`, `dotnet test` and `mix test`. The reviewer command policy refuses shell syntax, programs run by path, inline code, download launchers, setup commands and a script that this run changed; each refusal has a named row. A plan whose gate names a refused command goes back to the planner. `validation.end_checks` (Settings: *End-of-run checks*, default on) turns the gate on or off. See [Reviewer checks](./docs/CONFIGURATION.md#reviewer-checks).
- **Pre-existing failures are told apart.** While the briefs build, the project gate runs once on a copy of the run base, one command at a time, and the build block shows `Base re-run V1` with its clock. A red reviewer check is compared with that result, so the review does not wait for a second run; it waits only when that base command has not finished. A failure that is red there too is reported as pre-existing and starts no fix. A failure that the base cannot compare, such as a timeout or a red that names no failing test, reads *not verified at the run base*, and the reviewer decides.
- **A fix check answers only its own failures.** A fix task runs the red check it answers again. It passes when its own failures are gone, also when unrelated failures remain: `Fix check V1 · npm test · your 2 failures gone · 3 others left for their fix tasks or the next review`. When its own failures are all failing tests, it runs only their test files, and the next review runs the whole command.
- **`render` checks.** `validation.render` runs a render command for a plan's `render` check. The screenshots are saved with the session and go to the reviewer as images when its seat can take them, also on an API seat whose model reads images. The plan card, `splitbrief doctor` and a review seat change during the run say when the review seat cannot see the renders. A review that fails only for that reason names the REVIEW seat. Change the seat, then **Try again** runs the review on the new seat. A check that cannot run halts the run instead of reaching the review. Every check run is recorded in `evidence.json` and in the review's Checks Log.
- **Seat fallbacks.** A seat can declare `fallback: { tool, model?, effort?, variant? }`, chosen in Settings › Fallback. When a seat goes down on an account refusal or a usage limit, the run moves the seat to its fallback at once, once per run and seat. The fallback must be installed, signed in and not the seat itself. A headless run decides with `--on-seat-down halt|switch`. `splitbrief doctor --probe-seat <plan|build|review>` checks one seat with one real call.
- **Seat trouble is retried before a halt.** A network failure or a server error from the provider is retried up to ten times on every PLAN, BUILD and REVIEW call of a run. The wait between tries doubles from two seconds, and no wait is longer than one minute. When the provider names a wait, the run waits that long. A usage limit with a named reset and no fallback that the run can take waits for that reset, however long, also across a resume. Esc stops the wait, and a continue waits again until the same reset. A usage limit with no named reset and no such fallback halts with the seat picker.
- **Messages to the active seat.** Type a message and press Enter to queue it for PLAN, BUILD or REVIEW; the seat reads it at its next break. `ctrl+⏎` or `/steer <text>` stops the current call and continues with your text. Claude Code and OpenCode can take a message during a call. See [Input footer](./docs/FEATURES.md#input-footer).
- **Two halts.** Every recovery is one of two halts, **Needs you** or **Seat down**, and offers only the actions that fit its cause.
- **Runs are durable records.** A run is running, waiting for you, stopped, ready to apply or closed. Any open run continues with `splitbrief continue`, `/resume` or a bare `⏎`; only Apply, Discard or End run close it. Opening a run from `/sessions`, home or the palette shows its history on the run screen.
- **`splitbrief continue <id> --action <action>`** answers a recovery with no terminal attached: `skip`, `retry`, `switch-seat:<tool>[:<model>][@<word>]`, `end-run`, `apply`, `discard` or `restore`. It exits 1 while the run stays blocked, and 2 when the value names no recovery action.
- **A closed run ends with a summary.** The last rows of a closed run's transcript state the outcome, then one row for each stage: what the plan asked for, what the build did, what the review said and what changed. Each stage row ends with its time, and its label has the colour of its seat. The summary quotes the first two review notes and names every changed file when the run changed five or fewer. Otherwise it names three files: source files before test files, and the files that the most briefs changed first. One row counts what the summary leaves out, such as `+15 briefs · 62 files · 3 reviews · ctrl+a`. `ctrl+a`, `/activity` or a click on that row opens the whole record: every brief, note, earlier review and file. The rule under the transcript reads `Run closed` with the date and the time that the run closed, such as `Run closed · Nov 8, 20:48`. On a short terminal the summary keeps one row for each label. On a terminal too short for those rows, it leaves out whole rows, the crew first and then from the bottom up, so the outcome row and the row that opens the record stay on the screen.
- **Accept as is** for a failed final review, on every run. A checkout run closes; a worktree or staged-copy run becomes ready to apply with the open findings, and Apply asks once.
- **The stop sheet.** On the workflow screen, `esc` opens Stop options: **Stop now**, **Pause after this brief** and **End run**. No option reverts files, and your draft is kept.
- **Build progress block.** While briefs run, a block under the header shows the passed briefs of the total, what the seat is doing, and how long ago the seat last reported.
- **`--plain` output.** A headless run with `--plain` prints one plain-text line per phase. `--json` emits the NDJSON event stream.
- **Cursor Agent CLI (`cursor`), Command Code (`command-code`) and Antigravity (`agy`)** are supported CLI tools.
- **Skills for every seat.** `--skills <ids>` on `start`, `resume` and `continue`, or `/skills`, attaches project or global skills. Every seat call carries them.
- **An `on_halt` hook event**, fired when a run stops for recovery; `${event.resumeCommand}` substitutes into a hook's arguments.
- **Runtime commands** `/tasks`, `/resume`, `/end`, `/diff`, `/run accept|reject` and `/image`.
- **`@file` inputs may name a file anywhere:** an absolute path, a path relative to the project, or `~/…`. A missing, oversized or unreadable input stops `start` with one error that names every refused input and its fix.
- **Stack detection** for TypeScript, JavaScript, Python, Go and Rust. `validation.stack` pins a stack.
- **Typed seat answers.** Plans, reviews, consults and implementer reports are JSON answers that SPLITBRIEF validates, through each tool's native schema flag where it has one.
- **Private vulnerability reports.** The security policy describes how to report a vulnerability privately through GitHub.
- **`--plain` names a seat wait.** When a seat starts waiting for its usage limit to reset, `--plain` writes one line: `waiting: <tool> · resets <clock>`.
- **The model a Claude Code seat ran.** In the workflow sidebar, a Claude Code seat saved as a model alias, such as `opus`, gets one more row. The row shows the model id that the seat's call reported, such as `claude-opus-5-5`. A `shell` or `agent` seat with `stream-json` output that runs Claude Code gets the same row. Your saved seat value does not change.
- **REVIEW can be None.** Choose **None** for REVIEW in Settings › Crew, or write `reviewer: none` in `.splitbrief/config.yaml`. The run plans, builds each brief with its own checks, and ends with no review, no end-of-run checks and no render check. The run ends on one row, `Review · none`. Apply reads REVIEW from `.splitbrief/config.yaml`, or from `--reviewer` when the command passes it, each time it runs. With None, a merged result that your checkout also changed goes through its brief checks again, and a conflict stops Apply for you to resolve. These checks are part of Apply: while they run, at a stop and at rest, the run screen names Apply and takes no message. A run in your checkout has no Apply: a stop after its last brief names the review and takes no message. A brief whose only check is a `render` check has no verification. A move to None while a `Needs you` panel waits applies at once: **Review again** reads **Continue**, the next brief reads your typed words, and with no brief left the panel refuses them; a question for the fix's note closes, and the panel asks again. `splitbrief continue <id> --plain` names the same action. While `.splitbrief/config.yaml` does not load, the panel takes only **End run**, says why, and keeps your words.
- **Review cadence in Settings.** Settings › Workflow shows **Review cadence**.

### Changed

- **Review cadence and End-of-run checks are read-only while REVIEW is None.** Settings shows why.
- Prompt budget `auto` no longer stops a plan, a brief or a review on SPLITBRIEF's size estimate. The tool or the provider handles its own context. Set a Prompt budget to get the stop.
- A recovery answer that continues the run no longer adds a `Run continued` row under its Recovery row.
- A review result now puts one blank row between two findings.
- The build block shows the passed briefs without an attempt number. A halt names the attempts.
- **Supported Node.js versions.** SPLITBRIEF supports Node.js 22 and Node.js 24, and the package declares that range.
- **Scope is guidance.** A brief's files are suggestions. The implementer may edit another ordinary project file that the change needs, and SPLITBRIEF records it. Only a protected path asks: dependency manifests and lockfiles, `.git` and `.splitbrief`, CI configuration, and env or key files. It asks once per path per run.
- **A failed check goes straight to the planner.** A brief has no local retry before its consult. A correction that you send while the checks run goes to the next attempt. When the checks pass, the build tool gets one more attempt for that correction. `workflow.max_retries` is retired.
- **The work of a failed attempt stays.** A rewrite or a split from the planner keeps the files of the failed attempt. The new brief continues from them. When you skip the rewritten brief or the last open subtask, the files of the failed attempts go back. The results of completed subtasks and of fix tasks between them stay, and so do your own edits during a pause. A halt keeps these files, so Try again continues from them.
- **A check fails its brief only on a new failure.** A failure is new when it was not already red before the run. A red check with a new failure fails its brief, and before a review it goes to the reviewer. A red check whose failures were all red before the run passes. SPLITBRIEF compares the failures only when a check runs the same command as the project gate. Any other red check fails its brief on every failure. A check that cannot run halts the run.
- **`workflow.approve` is `plan | none`** (default `plan`). Retired keys load with one notice each and are ignored: `workflow.mode`, `workflow.task_review`, `workflow.brief_review`, `workflow.speckit`, `workflow.max_retries`, `approval.enabled`, `approval.tiers`, the `escalation` block, `validation.typecheck`, `validation.lint`, `validation.test`, `validation.typecheck_command` and `validation.lint_command`.
- **A seat call has no default time limit.** No seat has a default total timeout or idle cut. The watchdog warns after 5 minutes without output, and the build block reads `No output for m:ss`. `timeout`, `idleKillMs` and `maxToolCalls` are opt-in limits. Two timeouts or idle cuts in a row on one brief halt the build as *Seat down*.
- **Checks, API calls and hooks have no time limit by default.** Set `validation.timeout_ms`, the seat `timeout` or a hook `timeout_ms` to add one.
- **Hooks that set no `timeout_ms` ask for approval once more after the update.**
- **A tool's version or sign-in check waits up to a minute.** After 10 seconds the screen names the tool and the check it waits for. A command without a screen writes the same line on stderr. A sign-in check that does not answer lets an interactive start go on; a headless start needs `--allow-unverified-auth`. A version check that does not answer stops the start.
- **No count of tool calls ends a seat call by default.** A call with more than 256 tool calls now completes. The new `maxToolCalls` seat field stops a call after a set number of tool calls, and the error names that number and the last tool calls. A `shell` or `agent` seat with `text` output reports no tool calls, so SPLITBRIEF warns that the field is not used there.
- **A large answer or large output no longer stops a call.** An answer of up to 64 MB is kept whole, and only its copy in the call log is cut. A tool that writes more than 64 MB keeps running, and SPLITBRIEF still reads its final answer.
- **CLI reviewers read the change from a file.** A review seat on Claude Code, Codex, Cursor, OpenCode, Kilo Code, Command Code or Antigravity reads the diff from a file, in a run and in `splitbrief review`, so a large change is not cut short in the review prompt. Other review seats take the diff in the prompt. When a reviewer refuses the review as too large, the halt names that file instead of the largest diffs, because the prompt holds the plan, the briefs and the evidence.
- **Fix cycles go on until the review passes.** The run no longer stops after two fix cycles. Each time a review round makes no progress, or a review fails with no blocking finding on criteria no check verified, the planner decides the next step with its earlier answers in view: it adds guidance to the next fix briefs, writes new ones, runs a check again that may be flaky, asks you a question, accepts the open findings with a note (never while a red check or an Apply conflict still blocks), or says they cannot be fixed. When it says they cannot be fixed, the halt names the findings and the planner's reason: `Final review made no progress on F1, V1.1 after fix cycle 3` and `Planner said: …`. When it accepts them, the review stays failed and the run goes on as after your own **Accept as is**: a worktree or staged-copy run is ready to apply as is, a run in your checkout closes, and a task-cadence review lets the next brief start. The transcript, `review.md`, the closed run's summary and the Apply as is confirmation show the planner's note. A headless run exits 1 after an accept and writes the note in its `final_review_failed` record. **Review again** with a note sends the note to the reviewer, which judges the change again.
- **Each brief runs its own quick checks.** With `workflow.review: end`, a brief runs its own checks, such as its test file or the typecheck, when it hands back, so a broken type or test is fixed in the brief that caused it. A red check sends the brief to the planner. `render` checks still run before the review, and the full gate runs once before the review.
- **A check that already ran on the same files does not run again.** One command under several check ids runs once, a reviewer check takes the run of the same command before the review, and a continued run takes the run base results it already has. A stop and a continue keep every finished check. The row shows when the command ran, for example `reused, ran 11:53`. A changed file, a timeout, a stop and a `verify` of a red check run the command again.
- **Checks inherit your environment without credentials.** Provider API keys, cloud credentials, tokens, SSH sockets and Git credential helpers stay out; project settings such as `NODE_OPTIONS` and `DATABASE_URL` stay. See [What a check can reach](./docs/CONFIGURATION.md#what-a-check-can-reach).
- **SPLITBRIEF's own git calls keep only the git variables that reach a remote or a checkout filter:** protocol, SSH, askpass, proxy, SSL and HTTP settings, and the Git LFS skip settings. Other `GIT_*` variables, such as `GIT_CONFIG_GLOBAL`, `GIT_TRACE` and `GIT_EDITOR`, and `EDITOR`, `VISUAL`, `PAGER` and `PREFIX` no longer reach them; put such a setting in your git config. See [What SPLITBRIEF's git calls receive](./docs/CONFIGURATION.md#what-splitbriefs-git-calls-receive).
- **The Claude Code implementer never runs unsandboxed.** A sandbox that cannot start stops the seat. On Linux, readiness names a missing `bwrap` or `socat` before a run with that implementer starts. `splitbrief spec` and `splitbrief review` do not need them.
- **An inline `shell` or `agent` runner asks for trust once more after this upgrade.** It no longer inherits the SPLITBRIEF environment; it gets its staged environment and the names in its `env` list. A headless run stays blocked until you confirm in a terminal or pass `--allow-repo-runners`.
- **Briefs are grouped by outcome, not by count.** One brief delivers one reviewable outcome with its tests, wiring and documentation, and a run may hold any number of briefs.
- **A run creates no branch.** The run worktree is detached at your project's current commit. Create a branch yourself when you want the changes on one. A run that an older version started on a `splitbrief/<slug>` branch still continues, and closing it deletes that branch.
- **Staged-copy runs need no git.** A project without git no longer halts at its first brief. `splitbrief init` no longer writes `workflow.isolation`; unset reads `worktree`.
- **Old runs continue as one planning session.** A run that stopped at its spec, plan or briefs gate continues as one planning session that reads its earlier documents. A run saved before the typed plan and the run workspace still opens, but it loses the transcript rows of retired events (user edits, brief quality and readiness, pause selections) and its drift score.
- **One transcript, in time order.** Done, running and pending work reads in one scroller. A review row names its failed commands, failed checks and fix briefs. Event labels use sentence case; seat tags stay upper case.
- **One screen for a run, live or at rest.** The summary screen is gone. A stopped run stays on its run screen, and typing a correction continues it in place. A closed run ends its transcript with a summary of the run.
- **One name per seat on every surface.** `PLAN`, `BUILD` and `REVIEW` are the only seat words, and every surface names a seat as `<tool> · <model>` with the model's catalog label, for example `Claude Code CLI · Opus 5.5`.
- **An inherited review seat reads `REVIEW = PLAN`** on home, in Setup and Settings, in the picker and in the workflow.
- **Claude Code model aliases follow the current Claude Code CLI models.**
- **Settings.** Crew is the first section of Settings, with one row per seat, and the same rows build the first-run Setup screen. Settings explains the row under the cursor. Ready-made crews are offered in Setup.
- **The tool and model picker.** Effort, speed and thinking variants of a model are one row that expands into one child per option; effort is chosen there and shown read-only everywhere else. Providers route inline and show their sign-in state. A tool that cannot list its models says so, and a model with no display name shows its catalog name.
- **Readable terminal colours.** Secondary text stays readable on dark and light terminals. The TUI follows the terminal background and uses no faint text.
- **Layout.** Panels take their width from the terminal size. The workflow screen aligns every left edge on one column, and the workflow composer and transcript stay full-width.
- **23 runtime commands in five categories.** `/crew` opens Settings on PLAN, and `/crew <seat>` opens that seat's picker. On a recovery panel, **Change PLAN tool** (or BUILD or REVIEW) opens that seat's picker.
- **Every CLI tool takes its prompt on stdin.** Antigravity, Cursor, OpenCode, Kilo Code and Command Code now read it there too, so a large prompt no longer meets the command-line limit. An expired Codex or Claude Code planner session continues once on a fresh session with the conversation so far.
- **`shell` and `agent` runners always take the prompt on stdin, with no size limit.** A `shell` or `agent` runner whose `args` contain `{prompt}` no longer loads; before, the prompt was put into that argument.
- **CLI model lists keep a model through one missing read.** A model is added at once and removed only after two agreeing reads.
- **Flag precedence is stated.** `--planner`, `--implementer`, `--provider` and `--reviewer` help states that a CLI tool id always selects the CLI. A `--*-api-base` flag on a non-API seat warns and is ignored.
- Home shows no recent-sessions section when there are none.
- Show diff keeps less open on its own screen with its `Press q to return.` prompt, also when `LESS` or `PAGER` sets `-e`, `-E`, `-F`, `-m`, `-M` or `-X`.
- **How long a run ran is stated once, when it closes.** The workflow header and sidebar no longer show a clock for the whole run. A closed run states the time of each stage on its stage row, and its whole record states how long the run ran, for example `Ran 1m 51s`. Time the run sat stopped, halted or at rest is left out, and time it waited on you while it ran counts. A run recorded before this release reads `Ran not recorded`.
- Ctrl+Delete and Alt+Delete in the composer and other text fields delete the word after the caret, as in the plan.json editor. Before, they deleted the word before it.
- When a brief fails again, the planner or reviewer now sees every change the brief made since it started and one line for each earlier failed attempt, not only the latest attempt.
- With `review: task`, each task review first runs again the checks of the briefs it covers and of the criteria due at that review. A later brief that breaks an earlier brief's check is now found at that task review, not only at the final review. A run takes longer by these checks.
- `continue --action restore` says how many files it put back in your checkout, works without a terminal, and leaves the run ready to apply.
- A headless run stopped by Ctrl+C, SIGTERM or a closed terminal exits with code 130, 143 or 129 and prints the command that continues it.
- The model list in the picker, the provider scan on home and setup, the Check of a local server and the check of an API seat wait up to one minute instead of two or five seconds. A provider that answers after six seconds is now found, not failed. After ten seconds the screen names the provider and the check, also while a run checks its seat at its start or before a brief. Esc stops the check; during a run, the run's stop ends it.
- The workflow sidebar shows no waiting row. Before the plan names its briefs, the Tasks panel shows only `No tasks yet`. The header and the line under the composer show the stage.
- **Fewer warning rows.** A plan that goes back to the planner once, an output limit of a tool call, and a format pass that rewrote files no longer show a warning row. With `SPLITBRIEF_DEBUG` set, the [debug log](./docs/TROUBLESHOOTING.md#debug-environment-variables) records them; for a format pass it names the files.
- The activity list no longer shows a warning for an unknown upstream record or for the live-update limit of a call.
- A retry after a network or server failure shows on the status line and leaves no row in the transcript.
- **The plan, review and consult calls use git only to read**, as the build already does: status, diff, log and show. The plan rules also name the two forms of a `node` check that the command policy accepts: `node --test <test file>` and `node --check <file>`.
- **A project with no commits** now tells you: *Make a first commit of your files, then start again.*
- **The review checks the tests a brief adds.** For each test that a brief adds, the review checks that the test fails when the behaviour the brief names breaks. A test that still passes with that behaviour broken is a finding. The review in the `splitbrief`, `splitbrief-run` and `splitbrief-review` skills checks the same.
- **A brief's own check names the brief.** While a brief runs its own checks, the check row reads `T007 check K034 · npm test`. A check id that already starts with the brief id names the brief once: `Check T007-K1 · npm test`. Before, it read `Plan check K034`, with `Plan` in the color of the planner, as if the planner were on a call. Before review, a plan check still reads `Plan check K034`. Every check name now shows in the same color, except `Reviewer` in a reviewer check. Headless text output names the brief too, for example `T007 check K034: 1 new, 2 pre-existing (npm test)`.
- When you quit a run that is not closed, the shell now shows the command that continues it: `Continue this run with: splitbrief continue <id>`.
- When a run still runs in another window, every command now says the same thing: `Run <id> is still running. Stop it in the window that runs it, then run 'splitbrief continue <id>'.` Before, each command used its own words, and one told you to delete a file, which does not stop the run.
- **A new project builds with a CLI tool.** On a first run with no config, the BUILD seat takes the first ready tool. It tries Claude Code, Codex and OpenCode first, then the other tools that SPLITBRIEF lists. A config with no `implementer` block builds with Claude Code.
- The command list describes `/steer` as `Send a correction now; a running call stops first`.
- The workflow guide says what happens when a stop ends while the composer holds text: no menu opens, and the keys stay in the composer.

### Removed

- Workflow modes (`quick`, `standard`, `speckit`, `instant`), the step chain (research, spec, clarify, constitution check, analyze), the spec and briefs gates, and the flags `--mode` and `--approve`.
- The hint rung and the intermediate escalation tier, with the `escalation` crew row and picker.
- Sticky approvals, `.splitbrief/approvals.json`, `splitbrief approval` and `--yolo`.
- Budget gates, cost prediction, savings figures and price-based implementer routing; `Ctrl+G` and `/cost`. Spend is reported as one plain figure when prices are known.
- The summary screen, the standalone Crew overlay and the mode selector.
- The runtime commands `/redo-task`, `/effort`, `/repomap`, `/attach`, `/detach`, `/mode`, `/revise-spec`, `/revise-plan`, `/approval`, `/compact-transcript`, `/export`, `/handoff` and `/yolo`, and the aliases `/config`, `/planner`, `/implementer`, `/reviewer`, `/accept-run` and `/reject-run`. ## [0.1.0] - 2026-08-07

Initial release, installed from source. Everything in this section and the dated sections below it is what 0.1.0 contains.

### Fixed

- The repo map extracts symbols from Python, Go and Rust again. Each language now uses its own grammar package, which is also smaller, and Go type declarations are found.
- Readiness no longer headlines a missing, untrusted, incompatible, unauthenticated or unreachable runner with `Required action: Exit`; it names `Set up the configured runner`.
- The start gate names the tool and its install URL when a CLI is missing.
- `npm install -g splitbrief` no longer downloads and builds `node-pty`, which no shipped file uses.
- A cloned repository can no longer grant itself hook execution. Hook trust receipts live in `~/.splitbrief/trust/hooks.json` (mode `0600`), keyed by the checkout path. A receipt inside `.splitbrief/` is ignored: trust those hooks once more and delete the file.
- The hook trust prompt shows each hook's executable, its resolved path, its arguments and its trust boundary, with repository strings escaped. `--allow-hooks` writes the same disclosure to stderr.
- Multi-line trust disclosures keep their line breaks in the TUI approval prompt.
- Readiness no longer reports a CLI runner as authenticated because of files that the probe itself wrote.
- The Claude Code subscription `session` channel works on macOS, where the credential is a login-keychain item. It is the default on every platform again. On macOS it keeps your real `HOME` and `USER`, so the tool's reads and state writes reach your real home ([API-KEYS.md](./docs/API-KEYS.md)).
- Readiness never infers a keychain login from directory contents; it runs the tool's own status command.
- Readiness and the start gate name the missing credential and the command that supplies it, for example `Export ANTHROPIC_API_KEY …`.
- The detection cache works for a runner on the `api-key` channel.
- Every command resolves the project to the git top level, so running from a subdirectory such as `packages/web` no longer reports a missing config or creates a second `.splitbrief/`.
- A mistyped subcommand no longer starts a workflow named after the typo: `unknown command 'doctro' — did you mean 'doctor'?`. `splitbrief "fix the typo"` still runs.
- SPLITBRIEF refuses a Node.js older than 22 with a clear message.
- The documented `kind: api` examples load, with `service` and `offering`.
- `docs/GETTING-STARTED.md` describes only the spend surfaces that exist.
- A Task Brief quality failure in a headless run no longer loops: the planner regenerates the briefs once, and a second failure stops with every issue named.
- A first run on a machine without Ollama no longer prints `detectContextLength(ollama): fetch failed`.

- **The final review is its own seat.** An optional `reviewer:` block names the runner that reads the run diff, so a model from another lab can review the build.
